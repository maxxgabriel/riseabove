# Rise Above: desktop client

A Tauri 2 shell around a React and TypeScript interface. The interface never reads the simulation
directly. It calls one endpoint, `Api::call(method, args)` in `crates/pw-view`, which answers with JSON
that already respects what the person may know: an observer sees everything, someone inhabiting a player
sees what that player could know, and every sentence is rendered from recorded state by `pw-narrate`.

```
app/src            React interface (Vite, TS strict, hash router, no UI framework)
app/src-tauri      desktop shell; one command forwards to pw-view (not part of the Cargo workspace)
app/e2e            browser tests that drive a real server with Playwright
crates/pw-view     the API: pages, generic table queries, actions, inbox
crates/pw-serve    the same API over local HTTP, for development and the browser tests
```

## Run it

Browser, with hot reload:

```
cargo run --release -p pw-serve -- --data ./saves        # API on :8787
cd app && npm install && npm run dev                      # interface on :5173, proxies /api
```

Without Node, serve the built interface from the same process:

```
cd app && npm install && npm run build
cargo run --release -p pw-serve -- --data ./saves --static app/dist
```

Desktop app (needs the platform webview toolchain, see the Tauri prerequisites):

```
cd app && npm install && npx tauri build
```

`tauri build` bundles the interface into the binary. A bare `cargo build --release` in `app/src-tauri` would open the
dev-server address instead and show a blank page, so use `--features custom-protocol` there.

No game data ships with the project. "New world" offers a generated world; "Import" reads a folder in the
format described in `data/IMPORT_FORMAT.md`.

## How the interface is organised

- **Observer and inhabited modes** share every page. Inhabiting a player adds *My career* (today, messages,
  calendar, football, contract) and *My life* (life, people, press and fans, social, journal).
- **Tables** are one component (`TableView`) over one query (`table.query`): sort, filter, column presets and
  virtual scrolling come from the server's column description, so a new list is a Rust `Source` plus a route.
- **Decisions and replies** show the options the simulation generated. A reply is not typed text: it becomes
  an intent that the world applies on the next day by the same rules it applies to the AI. What is queued is
  listed on Today until then.
- **Society** lists everything that grew up around the game (posts, chants, rivalries, incidents, press,
  referees, records, tactical schools, lower football). The grapevine list is for observers only.
- **Help → What the simulation covers** is generated by the API (`capabilities`) and marks anything that is
  partial or missing. Nothing is drawn for a system that does not exist.

## Checks

```
cd app
npm run typecheck && npm test          # types and unit tests
npm run build && node e2e/smoke.mjs    # every route on a fresh world, fails on console errors
node e2e/inbox.mjs                     # plays until a decision arrives, answers it, replies to a conversation
node e2e/shots.mjs name=#/route ...    # screenshots into e2e/shots (SCHEME=light, W=, H=, DENSITY=, SCALE=)
```

The e2e scripts expect the server on `http://127.0.0.1:8787` with `--static app/dist` (set `BASE` to change
the address) and use the Chromium at `CHROMIUM`, which defaults to the one under `/opt/pw-browsers`. They
replace the open world.
